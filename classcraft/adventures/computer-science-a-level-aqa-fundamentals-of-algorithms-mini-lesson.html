4.3 · Complexity

Big-O — the language of comparison

Big-O describes how the run time (or memory) of an algorithm grows as the input size n grows. It is about the shape of the growth, not the exact number of steps: constants and lower-order terms are dropped, because for large n they stop mattering.

3n² + 500n + 9000 → O(n²)
OrderNameExample
O(1)constantarray access, hash lookup
O(log n)logarithmicbinary search
O(n)linearlinear search
O(n log n)linearithmicmerge sort
O(n²)polynomialbubble sort
O(2ⁿ)exponentialbrute-force subsets
O(n!)factorialbrute-force travelling salesman

Read it properly: O(n²) means "grows no faster than n squared" — it is an upper bound on the worst case. Doubling n makes an O(n²) algorithm take four times as long, but an O(log n) algorithm take just one extra step.

4.3 · Searching

Linear and binary search

Linear search inspects each element in turn until it finds the target or runs off the end. It works on any list, sorted or not. Worst case: n comparisons — O(n).

Binary search requires the list to be sorted. It checks the middle item; if the target is smaller it discards the whole upper half, otherwise the lower half. Each comparison halves the search space.

low ← 0 : high ← n-1 WHILE low <= high mid ← (low + high) DIV 2 IF a[mid] = target THEN RETURN mid ELSE IF a[mid] < target THEN low ← mid + 1 ELSE high ← mid - 1 ENDWHILE RETURN -1
max comparisons = ⌈log₂(n + 1)⌉1 000 000 items → only 20 comparisons

Binary tree search is the same halving idea on a BST: at each node go left if smaller, right if larger. O(log n) on a balanced tree; O(n) if the tree has degenerated into a chain.

The catch: binary search needs sorted data, and sorting costs O(n log n). Sorting once to search many times is a win. Sorting to perform a single search is not.

4.3 · Sorting

Bubble sort and merge sort

Bubble sort makes repeated passes, comparing adjacent pairs and swapping them if they are out of order. After pass 1 the largest item has bubbled to the end, so each pass can examine one fewer element.

comparisons = (n−1) + (n−2) + … + 1 = n(n−1)/2 → O(n²)
  • Best case (already sorted, with a "swap made?" flag): one pass, O(n).
  • Worst / average: O(n²). Space: O(1) — it sorts in place.

Merge sort is divide and conquer: split the list in half, recursively sort each half, then merge the two sorted halves by repeatedly taking the smaller of the two front elements.

  • Splitting produces log₂ n levels; each level merges all n items → O(n log n) in every case.
  • Space: O(n) — it needs a temporary array. Bubble sort does not.

The honest trade-off: merge sort is far faster on large data but uses extra memory and is harder to code. Bubble sort is trivial to write and needs no extra space, but is unusable beyond a few thousand items. There is no free lunch — you trade time against space.

4.3 · Graph traversal

Breadth-first and depth-first search

Both traversals visit every reachable vertex exactly once; both keep a visited set. The only difference is the structure holding the frontier:

Breadth-first (BFS)Depth-first (DFS)
Uses a queue (FIFO)Uses a stack (LIFO), or recursion
Visits all neighbours, then their neighbours — expanding in ringsPlunges as deep as possible, then backtracks
Finds the shortest path in an unweighted graphNatural for maze solving, topological sort, cycle detection
Can use a lot of memory (whole frontier queued)Memory proportional to the depth

Both are O(V + E) using an adjacency list.

Exam trap: BFS finds the fewest edges, not the lowest cost. On a weighted graph the fewest-edges route can easily be the most expensive one — that is exactly why Dijkstra exists.

4.3 · Optimisation

Dijkstra's shortest-path algorithm

Dijkstra finds the shortest path from one source vertex to every other vertex in a graph with non-negative weights.

  • Set the source's distance to 0 and every other to ∞. Mark all unvisited.
  • Take the unvisited vertex with the smallest distance (a priority queue does this).
  • Relax each of its edges: if distance(current) + weight < distance(neighbour), update the neighbour and record the current vertex as its predecessor.
  • Mark the current vertex visited — its distance is now final. Repeat.

Use the predecessor pointers backwards from the destination to reconstruct the route.

Why non-negative weights matter: Dijkstra assumes that once a vertex is finalised no shorter route to it can appear. A negative edge could later reduce that distance, breaking the assumption — so Dijkstra is simply wrong on graphs with negative weights. A* is Dijkstra plus a heuristic estimate of the remaining distance, which steers the search towards the goal and explores far fewer vertices.

4.3 · RPN

Reverse Polish notation

Reverse Polish (postfix) notation puts the operator after its operands: 3 4 + instead of 3 + 4.

Its virtues:

  • No brackets are ever needed;
  • no precedence rules are needed;
  • it is evaluated by a single left-to-right pass using a stack.

Evaluation: read left to right. Push every operand. On meeting an operator, pop two values, apply the operator (second-popped op first-popped), and push the result.

Evaluate: 6 2 / 3 4 * + 6 push 6 stack: 6 2 push 2 stack: 6 2 / pop 2, pop 6 → 3 stack: 3 3 push 3 stack: 3 3 4 push 4 stack: 3 3 4 * pop 4, pop 3 → 12 stack: 3 12 + pop 12, pop 3 → 15 stack: 15

Link back: the post-order traversal of an expression tree is the reverse Polish form. That is not a coincidence — both put the operator after its operands.

The big ideas to know

Big-O: O(1) · O(log n) · O(n) · O(n log n) · O(n²) · O(2ⁿ) · O(n!) — drop constants and lower terms

Searching: linear O(n), any data · binary O(log n), needs sorted data · BST O(log n) balanced

Sorting: bubble O(n²) time, O(1) space · merge O(n log n) always, O(n) space

Traversal: BFS = queue = fewest edges · DFS = stack = deep then backtrack · both O(V + E)

Dijkstra: relax edges from the closest unvisited vertex; non-negative weights only; A* adds a heuristic

RPN: operator after operands · no brackets or precedence · evaluate with a stack · equals post-order
